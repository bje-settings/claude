# tests/plugins/gh/fixtures

This is the captured contract for the TypeScript sync commands. Everything here came out of the
Python that is still in the tree at `plugins/gh/scripts/`, **before** anyone ported any of it.
#127 layer 4 deletes that Python. A fixture edited to fit the port would prove the port against
itself.

Nobody edits the three CAPTURES (`bash-output.json`, `bash-sync-output.json`,
`python-cli-output.json`) after the capture commit. `divergences.json` is not a capture. It is the
table of what the port deliberately says instead. It grows when someone finds a divergence. That
is the only way a divergence stays countable, instead of turning into a silently rewritten
expectation.

`vitest` and the coverage reporter both exclude `**/fixtures/**`, so these files are data the tests
read and never code that runs.

| File | Where it came from |
| --- | --- |
| `bash-output.json` | Copied byte for byte at `02fadf3` from `tests/gh/golden/bash-output.json`. It captures `gh-sync-repo.sh`'s output, from before anyone deleted the shell script, over the scenarios in `tests/gh/scenarios.py`. It normalises out commit hashes and the sandbox path. |
| `bash-sync-output.json` | Copied byte for byte at `62799d0` from `tests/gh/golden/bash-sync-output.json`. The same capture, for `gh-sync.sh`, over the scenarios in `tests/gh/test_gh_sync.py`. |
| `divergences.json` | The divergence table of `tests/gh/test_output_parity.py`, ported here as data. It adds what the pnpm-only ruling does to three scenarios' inputs, plus two tables the Python never needed: `ghVocabulary`, the report lines that now read in `lib/gh.ts`'s words instead of `gh_json`'s, and `inProcessFanOut`, the one line that replaces the three the child process took with it. The test that asserts each one reads it. |
| `python-cli-output.json` | Generated by running `plugins/gh/scripts/gh-sync.py`, `gh-sync-repo.py`, and `lib/discover.py` over the states their own tests build, at `cb8fb06`. The capture then normalises it the same way, and biome formats it, touching only whitespace, because this directory sits inside the formatter's scope, while `tests/gh/golden` sits outside it. It holds the contracts the two goldens do not: argument refusals, their exit statuses, the help text, and discovery's own stdout. |

`subcommands/sync-repo.*.test.ts` read `bash-output.json`. `subcommands/sync.*.test.ts` read
`bash-sync-output.json`. Both also read `divergences.json`. Those two, plus `discover.test.ts`,
also read `python-cli-output.json`. Each parity test lives with the other tests of the command it
covers, under `tests/plugins/gh/subcommands/`. That is the layout rule in
`.claude/rules/type-ts.md`.

## Why a capture and not a second suite

The acceptance line on #127 is that the port's output is byte-identical on the same repository
state. A test that asserted the port's own strings would pass whatever the port printed. These
files are the only record of what the Python printed that survives layer 4, so the capture commit
comes first, alone, and the tests check every later commit against it.

## What the goldens do not prove

`bash-output.json` records one shell run per scenario. Where the port deliberately says something
else, `divergences.json` names the line that changed, and why. This keeps a divergence countable,
instead of letting it turn into a silently rewritten expectation. Three scenarios build a
`package-lock.json` in the Python. Under the pnpm-only ruling, the port builds `pnpm-lock.yaml`
for the same state, but the reported line stays the same. That is why the golden still applies to
them.

The goldens also cover no state that only a `gh` failure, or a job that threw, can produce. So the
`ghVocabulary` and `inProcessFanOut` tables carry those instead. `subcommands/sync-repo.*.test.ts` map
the first into their own examples. `subcommands/sync.*.test.ts` read the second. A new divergence, or a
change to one of these, must be recorded here before the suite goes green.

Each `ghVocabulary` line carries both halves of the failure the real client throws. `message` is
the whole of it. `account` is `GhError.detail`, the part without the `gh <argv> failed: ` prefix,
which is what the report quotes.

`ghVocabulary.closed` lists the two lines that stopped being divergences when `lib/gh.ts` added
that field. They form a list, not a sentence, because an example is driven from them too. That
example asserts two things: each state now reads in the Python's own words, and the line it used
to print appears nowhere in the report. This check is what prevents a quiet return of the old
lines to the table. The sentence this replaced claimed as much, but nothing enforced it.

`failureSummary` is #81's table. It states the new stderr wording. It does not substitute for an
old one, because there is no shell or Python line it replaces. #218 finding 8 removed
`exitStatus`: the arms it once described read a non-zero job status that nothing could ever
produce, and both are gone.

## `deleted-cwd.ts`

`hook.test.ts` runs the hook entry point through this fixture. The fixture enters a directory,
removes it, and then imports the hook. So `process.cwd()` throws, and the test proves that the
entry point's outermost handler still exits 0.

## `throwing-sync-entry.ts`

This is a `.ts` fixture, not a JSON one, like `deleted-cwd.ts`. The suite that needs it has no
other place to put a program.

`syncRepo`, the real job, never throws through any state a test can reach from the outside.
(`lib/process.ts`'s `run` never rejects. Every git call answers `null` on failure, instead of
throwing. Every `gh` failure arrives as a `GhError`, which `sync-repo.ts`'s `ask()` always
catches.) So `tests/plugins/gh/bin.test.ts`'s one spawned case, for the #81 exit-1 contract,
imports the real `createSyncCommand` with a stand-in that throws in place of `syncRepo`, in a real
process rather than in-process.

What it proves is narrower than "the same production wiring `scripts/gh.ts` uses". `scripts/gh.ts`'s
own `write` helper is an unexported `const`, and its `sync` dispatch arm is a dispatch branch;
neither one imports from outside that file. So this fixture MIRRORS that wiring, rather than
calling it. (Review round 1, #165, proved this: it mutated `scripts/gh.ts`'s `write` to always
return exit 0, and confirmed that the spawned test in `bin.test.ts` stayed green.)

A future edit to `scripts/gh.ts`'s `write`, or its `sync` arm, could break the exit-1 case, and
this fixture would not catch it. Only an edit that also broke one of the OTHER spawned
`bin.test.ts` cases (the refusals, `--help`) would be caught, since those exercise the real
`write` at exit 0 and exit 2. To close this gap outright, `write` needs export from
`scripts/gh.ts`, or another way to import it; that is outside this fixture's own scope.
`vitest.config.ts`'s `**/fixtures/**` exclusion covers it, the same way it covers the other `.ts`
fixtures. So it is linted and type-checked, but never measured.

## `throwing-command-entry.ts`

The same gap, for #218 finding 7's top-level catch. No externally reachable command throws
through a spawned process with no `gh` reachable at all. So this fixture MIRRORS `scripts/gh.ts`'s
own `run` dispatch and its catch, over one command that always throws. A future edit confined to
that catch could break the exit-1, one-line, no-stack-trace contract without this fixture noticing.
